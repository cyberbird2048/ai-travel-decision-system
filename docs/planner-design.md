# 旅行规划师 · 规划层设计文档（v1.3）

> 本文档是规划层的产品与架构蓝图，交给执行方（codex）落地。当前仓库中的静态原型（index.html / engine/planner.js / h5.html）是 M0 骨架，本文定义 M1–M3 要长成什么样。

---

## 0. 定位与设计原则

**一句话定位**：一个替你做"出行决策"的规划师，不是一个订票聚合器。

四条原则，所有功能取舍都回到这里：

1. **决策优先于信息**。用户要的不是 30 个航班列表，而是"选这班，因为你不爱红眼且这班延误率低"。每个模块输出的是一条推荐 + 理由 + 一个备选，而不是数据堆。
2. **诚实优于完整**。拿不到可靠数据就明说（示例数据打标、超出预报窗口拒绝打分），永远不用编造的精确度换取界面好看。这是从 M0 继承下来的硬规则。
3. **草案优先于问卷**。不要在开头问用户 20 个问题。先用已知偏好 + 合理默认生成一版完整草案，让用户"改"而不是"填"——人对着草案表达偏好，远比对着空表单准确。
4. **记忆必须可见、可纠正**。系统记住的每一条偏好，用户都能看到、能改、能删。"越用越懂你"的前提是"你知道它懂了什么"。

## 1. 交互设计

### 1.1 核心交互模式：草案—批注循环（Draft & Annotate）

不采用纯对话式（开放聊天容易发散、成本高、难以结构化沉淀偏好），也不采用纯表单式（表达不了"我想要松弛一点"这类需求）。采用混合：

```
┌─ 需求输入（30 秒）──────────────────────────┐
│ 结构化：出发地/目的地/日期/人数/预算档       │
│ + 一句话自由文本："带爸妈，节奏慢，想吃好的" │
└──────────────┬───────────────────────────────┘
               ▼
┌─ 草案生成 ──────────────────────────────────┐
│ 完整计划：线路/航班/交通/清单/吃玩           │
│ 每个卡片带【理由】："给你排了 10:30 的航班， │
│ 因为你上次说不坐早班机"                      │
└──────────────┬───────────────────────────────┘
               ▼
┌─ 批注迭代（核心交互）────────────────────────┐
│ 每张卡片三个动作：✓保留  ⟳换一个  ✕不感兴趣  │
│ + 卡片级自由文本："这天太赶了"               │
│ 系统只重排被否决的部分，已确认的锁定不动     │
└──────────────┬───────────────────────────────┘
               ▼
┌─ 定稿 → 动态 H5 ─→ 行中调整 ─→ 行后复盘 ────┐
└──────────────────────────────────────────────┘
```

关键细节：

- **锁定语义**：用户点过 ✓ 的卡片在后续重排中不可变动（除非触发天气硬红线，此时高亮提示并给替代，仍由用户确认）。这让迭代收敛，也是最强的偏好信号。
- **理由是一等公民**：每条推荐必须能回答"为什么是这个"。理由来自三层：用户画像（"你偏好…"）、当次约束（"这天有雷暴"）、通用常识（"国际航班提前 3 小时"）。理由同时是记忆的展示窗口——用户看到错误的"你偏好…"可以当场纠正。
- **节奏滑杆**：一个显性控件（特种兵 ←→ 松弛），直接控制每日行程槽位数（5–6 个 vs 2–3 个）和步行预算。这是最常被表达又最难从文本推断的偏好，值得一个专属控件。
- **行中模式**：H5 在旅程期间打开时进入"今天"视图：当前时段该做什么、天气突变时推送替代方案、一键"今天不想动了"→ 重排当日为松弛版并顺延非必去项。行中的每次调整都是高价值偏好信号。
- **行后复盘**：旅程结束后 H5 变成复盘页：3 个问题以内（最喜欢哪个安排？哪个安排不该去？下次想改什么？），答案直接写入画像。不做长问卷。

### 1.2 三个界面的分工

| 界面 | 场景 | 职责 |
|---|---|---|
| 规划台（桌面优先） | 出发前 1–4 周 | 需求输入、草案批注、接口设置、画像管理 |
| 动态 H5（移动优先） | 出发前 3 天 ~ 行程结束 | 倒计时、当日视图、实时天气重算、清单勾选、行中调整、分享 |
| 复盘页（H5 内） | 结束后 | 3 问复盘、下次目的地种草 |

## 2. 接口选型

原则：每个能力域一个**接口抽象**（已有 registry.js），域内可换供应商；默认档永远可用（免 Key 或本地数据），付费档按需接入。规划的"大脑"（自然语言需求解析、行程组排、理由生成）用 LLM 完成，其余域接口只负责提供事实。

> **供应商选择以第 7 节为准**。本节写于 v1.0，记录的是"每个域需要什么能力、边界在哪里"；第 7 节（品牌工具层）用官方 MCP 替换了其中多数域的具体供应商——POI/交通走高德 MCP（国内）或 Google Maps MCP（海外），机酒走飞猪 skill。两节冲突时按第 7 节实现，本节仍是能力边界与取舍理由的依据。

| 能力域 | 默认（免 Key） | 推荐接入 | 备选 | 取舍说明 |
|---|---|---|---|---|
| **需求解析 / 组排 / 理由**（大脑） | 规则引擎（M0 已有） | **DeepSeek API**（deepseek-v4-pro，结构化输出 JSON） | 本地规则 | 自由文本→TripBrief、草案组排、理由生成、批注理解全靠它；用 tool-use 强制输出 schema，失败降级规则引擎 |
| 天气 | **Open-Meteo**（已接，16 天全球） | 保持 | HKO（香港警告叠加，已有） | 免 Key 且质量够用，无需更换 |
| 地理编码 / POI | 内置目的地库（已有 7 城） | **高德地图 Web API**（国内用户主场景，中文 POI 质量最好，个人 Key 免费额度大） | Google Places（海外深度）、OpenTripMap（全免费但质量弱） | 港澳台+海外华人常去目的地高德覆盖尚可；纯欧美长尾目的地再补 Google Places |
| 航班搜索 | 示例航线库（已有，明确打标） | **Amadeus Self-Service API**（免费额度 2000 次/月，有真实报价和航线搜索） | Duffel（可出票但重）、AviationStack（只有时刻没有价格） | 只做"搜索与推荐"，**不做出票**——出票的合规与售后成本不属于规划师；推荐结果深链到携程/Google Flights 完成购买 |
| 落地交通 | 内置知识库（已有） | 高德路径规划（国内/港澳）+ 内置库（海外机场进城是慢变化知识，人工维护性价比最高） | Google Directions | 机场进城方案变化频率低，知识库+定期人工校对比实时 API 更可靠 |
| 汇率 | — | **Frankfurter API**（免 Key） | exchangerate.host | 预算换算用，量小 |
| 节假日 / 签证提醒 | — | **Nager.Date**（免 Key，公共假期） | 内置签证常识表 | 只做提醒（"目的地当天是公众假期，景点会挤"），不做签证办理指导的权威承诺 |
| 酒店 | 不做搜索 | 只做**区位建议**（"住尖沙咀，因为你的行程 60% 在九龙"），深链 Booking/携程 | — | 酒店报价接口贵且卷，区位建议才是规划师的价值 |

**接入优先级**（给 codex 的顺序）：Claude API（大脑）→ 高德 POI → Amadeus 航班 → 汇率/假日。每一步都保持"没有 Key 也能跑通"的降级路径。

### 2.1 LLM 的使用边界

- LLM 只产出**结构化 JSON**（TripBrief、DayPlan、Reason、ProfileUpdate），前端不直接渲染自由文本，避免幻觉污染事实字段。
- 事实（航班时刻、天气、价格、营业时间）一律来自域接口或知识库，LLM 只做**选择与解释**，prompt 中注入的事实带来源标记。
- 每次调用带上画像摘要（≤500 tokens）+ 当次约束，不带全部历史。
- 成本控制：草案生成 1 次调用；每轮批注只对被否决部分做增量调用；行中调整用轻量调用（haiku 档也可）。

## 3. 功能取舍

**做**（按优先级）：

1. 自由文本需求解析（"带爸妈节奏慢" → 结构化约束）
2. 草案—批注循环 + 卡片锁定
3. 带理由的推荐（每域 1 推荐 + 1 备选）
4. 偏好画像与记忆（第 4 节）
5. 行中动态调整（天气触发 + 用户触发）
6. 航班"推荐+深链"，酒店"区位建议+深链"
7. 多人出行画像叠加（同行人标签：爸妈/小孩/朋友 → 约束合并，取最保守）

**不做**（明确拒绝，防止范围膨胀）：

- ❌ 任何形式的**订票/支付/出票**——深链跳转到成熟平台
- ❌ 实时价格承诺与比价（价格快照标注抓取时间，声明"以平台为准"）
- ❌ 社交功能（游记、点评社区）——分享只到 H5 链接为止
- ❌ 签证/保险的权威指导（只做提醒 + 官方链接）
- ❌ 全球全目的地覆盖——目的地库按用户实际去处逐个做深，宁可 20 个城市做透，不做 2000 个城市的空壳

## 4. 越用越懂你：偏好学习机制

这是本系统区别于"又一个行程工具"的核心。设计成三层记忆 + 四种信号 + 一个可见的画像页。

### 4.1 记忆分层

```
┌────────────────────────────────────────────────┐
│ L1 稳定画像（跨旅程，慢变化）                    │
│ 航班时段偏好、节奏、预算档、饮食禁忌、           │
│ 晕车/怕晒等身体约束、常用出发地、同行人档案      │
├────────────────────────────────────────────────┤
│ L2 旅程上下文（单次旅程内）                      │
│ 本次已锁定/否决的卡片、本次特殊约束               │
│ （"这次带爸妈"不等于永远带爸妈）                  │
├────────────────────────────────────────────────┤
│ L3 事件日志（原始信号，只追加）                   │
│ 每次 ✓/⟳/✕、行中调整、复盘回答、清单勾选行为     │
│ L1 由 L3 定期蒸馏产生，可追溯                    │
└────────────────────────────────────────────────┘
```

### 4.2 信号来源（按可信度排序）

| 信号 | 例子 | 写入 |
|---|---|---|
| **显式声明** | 复盘回答、画像页手动编辑、"我不吃辣" | 直接写 L1，置信度 1.0 |
| **批注动作** | 连续 3 次 ✕ 早班机 | L3 → 蒸馏为 L1 候选（置信度 0.7），下次草案的理由里以"我注意到你似乎不喜欢早班机，这次避开了"的形式**展示并请求确认**，确认后升为 1.0 |
| **行中调整** | 两次旅程都在第 3 天触发"今天不想动" | 蒸馏为"连续高强度不超过 2 天"，同上需确认 |
| **弱行为** | 清单某项从不勾选、某类 POI 从不点开 | 只降权重，不生成画像条目，不向用户展示 |

### 4.3 蒸馏与衰减规则

- **蒸馏时机**：每次旅程定稿后 + 复盘提交后，跑一次"L3 → L1 候选"的 LLM 蒸馏（输入：本次事件日志 + 现有画像；输出：ProfileUpdate 列表，每条带证据引用）。
- **确认机制**：置信度 <1.0 的画像条目在下次使用时以理由形式露出，用户不纠正视为软确认（+0.1/次，上限 0.9），显式确认升 1.0，纠正即删除并记录反例。
- **衰减**：非 1.0 条目 12 个月未被任何旅程引用则衰减 0.2/年，降到 0.3 以下归档不再使用。口味会变，画像不能是化石。
- **场景隔离**：画像条目带场景标签（独行/带父母/带小孩/情侣），叠加同行人时按场景检索，避免"带爸妈时喜欢博物馆"污染独行画像。

### 4.4 画像页（用户可见）

一个独立页面，按"我了解到的你"来组织：

- 每条：内容 + 置信度（用"比较确定/猜测"两档展示，不露数字）+ 证据（"来自 3 月东京之行的 2 次选择"）+ 编辑/删除按钮。
- 底部一键"清空全部记忆"。
- 存储：M1 全部 localStorage（延续无服务端架构，导出/导入 JSON 支持换设备）；M2 若上账号体系再上服务端，本文不展开。

### 4.5 数据模型（给 codex 的 schema）

```jsonc
// TripBrief —— 需求解析输出
{
  "origin": "深圳", "destination": "东京",
  "dates": {"start": "2026-10-01", "end": "2026-10-05", "flexible": false},
  "party": [{"tag": "self"}, {"tag": "parents", "constraints": ["low-walking", "no-red-eye"]}],
  "budgetTier": "mid",            // low | mid | high
  "pace": 2,                       // 1 特种兵 … 5 松弛
  "intents": ["food", "culture"],
  "freeText": "带爸妈，节奏慢，想吃好的",
  "hardConstraints": ["no-red-eye"]
}

// PlanCard —— 一切推荐的原子单位
{
  "id": "flight-rec-1", "domain": "flight",   // flight|transit|slot|hotel-area|packing|poi
  "payload": { /* 域数据 */ },
  "reason": {"text": "避开了早班机，因为你带父母出行且此前多次跳过 8 点前航班",
              "sources": ["profile:no-early-flight", "brief:parents"]},
  "alternatives": ["flight-rec-2"],
  "state": "proposed"              // proposed | locked | rejected | replaced
}

// ProfileEntry —— L1 画像条目
{
  "id": "pref-014", "scene": ["with-parents"],
  "statement": "不接受 8:00 前起飞的航班",
  "confidence": 0.9,
  "evidence": [{"trip": "2026-03-tokyo", "event": "rejected flight-rec-3"}],
  "createdAt": "2026-03-12", "lastUsedAt": "2026-08-01", "status": "active"  // active|archived
}

// FeedbackEvent —— L3 事件（只追加）
{
  "ts": "2026-08-27T10:00:00Z", "trip": "2026-10-tokyo",
  "type": "card-rejected",        // card-locked|card-rejected|card-replaced|midtrip-adjust|review-answer|manual-profile-edit
  "cardId": "flight-rec-1", "note": "这班太早了"
}
```

## 5. 给 codex 的落地路线图

| 里程碑 | 内容 | 验收标准 |
|---|---|---|
| **M1 大脑+批注** | 接 Claude API（需求解析 + 草案组排 + 理由生成）；卡片化改造（✓/⟳/✕ + 锁定）；FeedbackEvent 日志落 localStorage | 输入一句自由文本能出带理由的完整草案；否决航班后只重排航班域，锁定项不动 |
| **M2 记忆** | 画像蒸馏（定稿后触发）；画像页（可编辑可删）；理由中露出待确认偏好；场景标签 | 第二次规划的草案能引用第一次的否决行为并在理由中说明；画像页删除条目后立即不再生效 |
| **M3 实时接口+行中** | 高德 POI、Amadeus 航班、汇率/假日；H5 行中模式（当日视图、天气触发重排、"今天不想动"）；复盘 3 问 | 无 Key 时全链路仍可跑（打标示例）；行中调整产生的事件进入下次蒸馏 |

**不变式**（每个里程碑都必须保持）：无 Key 可跑、示例数据打标、超预报窗口不打分、记忆可见可删、LLM 不产出事实字段。

## 6. 竞品对照与吸收（v1.1 增补）

对照了三类参照物：GitHub 开源旅行规划项目（Wanderlog 类、AI itinerary generator 类）、国内 OTA 的 AI 产品（飞猪"问一问"多智能体、携程/Trip.com TripGenie）、Booking.com 的 GenAI 套件（AI Trip Planner / Smart Filter / Property Q&A / Review Summaries）。共性优点及吸收方式：

### 6.1 吸收进本方案的 7 个模式

| # | 模式 | 来源 | 吸收方式（落点） |
|---|---|---|---|
| 1 | **地理聚类排程 + 地图一等公民** | Wanderlog（route optimize）、多数开源项目都有地图视图 | 组排新增硬约束：同一天的槽位必须在同一片区（POI 带 `geo` 与 `cluster` 字段），跨片区折返计为组排失败重排；规划台与 H5 各加一个逐日地图视图（高德 JS SDK / Leaflet+OSM 降级）。落 M1（约束）+ M3（地图 UI） |
| 2 | **自然语言即筛选器** | Booking Smart Filter（"要有屋顶酒吧和运河景观"→自动转筛选） | 批注动作 ⟳ 换一个支持带修饰词："换一个，要人少的" → LLM 解析为域过滤条件后再检索，而不是盲换。落 M1，PlanCard 增加 `swapHint` 字段 |
| 3 | **证据化推荐** | Booking Review Summaries、开源"evidence-backed itineraries" | Reason 之外增加 EvidencePack：每张 POI/酒店区位卡带评分快照、来源链接、1 句评论摘要（有接口时），无接口时标"知识库条目 + 最后人工校对日期"。落 M2 |
| 4 | **预算是一等约束** | 飞猪问一问（"带娃游成都，预算5000"→方案带精确费用） | TripBrief 的 `budgetTier` 升级为 `budget: {tier, amount?, currency}`；每张卡带 `costEstimate`；草案顶部常驻预算条（估算合计 vs 预算，超支时标红并指出最贵可替换项）。落 M1 schema + M2 UI |
| 5 | **域 agent 管线（不是营销叙事）** | 飞猪问一问的路线定制师/交通顾问/预算管理师分工 | 大脑从"单次大 prompt"改为管线：解析 → 各域检索（并行）→ 组排 → 预算核对 → 理由生成，每步独立可测、可降级。这是实现架构不是产品概念，界面上不出现"八个小助手"。落 M1 |
| 6 | **行中主动服务** | TripGenie（proactive trip management）、TripIt（travel-day info） | H5 行中模式加"时间敏感提醒轴"：值机窗口、酒店退房、末班车/末班快线、景点闭馆前 1 小时；数据来自计划本身推导（本地通知/日历，不依赖服务端推送）。落 M3 |
| 7 | **导出与轻协作** | Wanderlog（多人同编、离线、导出）、TripIt（ics 聚合） | H5 增加导出 .ics（逐日槽位进日历）与打印样式；分享链接升级为"同行人批注"轻协作：无账号，链接+昵称，同行人可对卡片投 👍/👎，回流为 FeedbackEvent（scene 标签自动带同行人）。落 M2.5 |

### 6.2 看到但明确不学的

- **一键下单闭环**（飞猪/TripGenie 的核心）：这是 OTA 的库存优势，不是规划师的价值；我们保持"推荐 + 带上下文深链"（日期人数预填进跳转 URL），把"从决定到行动"的距离缩到最短但不越过交易线。
- **对话式 LUI 为主界面**（TripGenie）：开放对话发散、偏好难沉淀，维持草案—批注为主、自由文本为辅。
- **多智能体作为产品卖点**（问一问）：吸收其架构，拒绝其叙事——用户面对的是一个规划师，不是一支团队。

### 6.3 对 schema 与路线图的修订

- `TripBrief.budget = {tier: "mid", amount: 5000, currency: "CNY"}`（amount 可选）
- `PlanCard` 增加 `costEstimate: {amount, currency, confidence}`、`swapHint: string|null`、`geo: {lat, lng, cluster}`
- `FeedbackEvent.type` 增加 `companion-vote`
- 路线图变更：M1 增加地理聚类约束、swapHint、预算 schema 与域 agent 管线；M2 增加 EvidencePack 与预算条 UI；新增 **M2.5 轻协作**（同行人批注 + ics 导出）；M3 增加地图视图与行中提醒轴。

## 7. 品牌工具层：CLI / MCP 接入（v1.2 增补）

一个重要的架构升级思路：与其为每个品牌手写 REST 适配器，不如直接消费品牌**官方发布的 Agent 工具**。调研结论：旅行品牌几乎没有出传统 CLI，但 2025 年以来集中在出 **MCP server / Agent skill**，这是同一思路的正确落点——它们本质上就是"给 AI 用的 CLI"。

### 7.1 已查证可用的品牌工具

| 品牌工具 | 形态 | 提供能力 | 对本方案的价值 |
|---|---|---|---|
| **高德地图 MCP Server**（官方，lbs.amap.com/api/mcp-server） | 云托管 MCP，免部署、自动升级 | 12 大接口：地理编码、POI 关键词/周边/详情搜索、驾车/公交/步行/骑行路径规划、距离测量、天气、IP 定位；结果已做语义化转换便于 LLM 理解 | **一个 MCP 顶掉三个自建适配器**（POI + 落地交通 + 国内天气交叉验证）；地理聚类排程的 geo 数据直接来自它 |
| **飞猪 AI 开放平台**（官方，flyai.open.fliggy.com） | 官方 skill / MCP，适配 Agent 生态 | 机票、酒店、景点、演出、签证全品类**实时库存与价格**，结果可真实预订 | 航班/酒店域从"示例数据"直接跳到"实时可订"，且天然带深链（结果自带预订链接，与我们"不做出票只深链"的边界完美契合） |
| **Amadeus MCP**（官方 API + 多个社区 server） | 本地/托管 MCP，需 CLIENT_ID/SECRET | 航班搜索、多城市、最便宜日期（cheapest dates）、机场/航司信息、价格优化 | 国际航线的补充与交叉验证；"最便宜日期"能反哺弹性日期建议（dates.flexible=true 时给出省钱改期方案） |
| **12306 MCP**（社区，多个实现） | 本地 MCP | 余票、车站、经停、中转换乘方案 | 补齐国内游最大盲区：高铁。深圳→香港、跨省国内线路的地面方案不再是知识库硬编码 |

### 7.2 架构落点：适配器的第三种模式

`AdapterRegistry` 的每个能力域从两档（sample / REST-key）扩展为三档：

```
sample（内置数据，打标） → rest（自管 Key 调 REST） → mcp（消费品牌官方工具）
```

- **大脑管线跑在 Agent 运行时**（Claude Agent SDK / Claude Code）时，MCP server 直接挂载为工具，域检索步骤由模型原生 tool-use 完成——这也意味着"域 agent 管线"（6.1-5）的检索步骤不用自己写编排代码。
- **纯网页端**（无 Agent 运行时）时，经一个薄 gateway（serverless 函数）代理 MCP 调用；M1 阶段可以先只支持 Agent 运行时，网页端维持 rest/sample 档。
- 统一约束不变：MCP 返回的仍是"事实"，选择与解释仍归大脑；每条结果记录 `source: {brand, tool, fetchedAt}`，证据链（EvidencePack）直接引用。

### 7.3 取舍与风险

- **官方优先**：高德、飞猪、Amadeus 官方渠道可直接依赖；12306 类**社区** MCP 标注"非官方"，只做查询不做代购，接口断供时降级回知识库。
- **不引入**：需要用户账号登录的爬虫型 MCP（合规与封号风险）、以及任何代替用户下单的工具（越过交易线）。
- **信任边界**：品牌 MCP 的返回视为外部数据，进 prompt 前做 schema 校验与截断，防注入；不同品牌对同一事实（如航班时刻）冲突时，以官方直连源优先并在理由中披露分歧。
- **路线图修订**：M1 的域检索直接以"高德 MCP + 飞猪 skill"起步（能省掉自建 POI/交通适配器的大半工作量），Amadeus/12306 移到 M3。

### 7.4 海外出行覆盖（v1.3 增补）

7.1 的组合对国内 + 港澳台够用，但**纯海外目的地不够**：高德的境外 POI 与公交路径覆盖弱，是最大缺口。按能力域逐一对齐海外工具后的完整矩阵：

| 能力域 | 国内/港澳台 | 海外 | 说明 |
|---|---|---|---|
| POI / 路线 / 本地交通 | 高德 MCP | **Google Maps 官方 MCP（Maps Grounding Lite）**：Places (New)、Routes v2、Geocoding、天气 | Google 官方已出 MCP，能力与高德 MCP 几乎一一对位；公交细节大部分城市可用 |
| 评论 / 评分 / 证据源 | 高德 POI 详情（评分） | **TripAdvisor Content API MCP**（官方 Content API，社区 MCP 封装成熟） | EvidencePack 的海外证据来源：评分快照 + 评论摘要 + 照片 |
| 机票 | 飞猪 skill | 飞猪 skill（覆盖国际线）+ **Amadeus MCP** 交叉验证 | 已覆盖，无缺口 |
| 酒店 | 飞猪 skill | 飞猪（国际酒店）为主；**不引入** Booking 社区 MCP | Booking 官方 Demand API 仅对 Affiliate 开放、门槛高；社区 MCP 多为爬虫/逆向，踩了我们"不引入爬虫型工具"的红线。区位建议用 Google Places 评分数据已足够，深链仍到 Booking/Agoda |
| 火车 / 城际 | 12306 MCP | 不做实时（欧铁/JR 无免费官方接口），落**知识库**：主要线路的时长/价格量级/购票官网深链 | 与"机场进城知识库"同一维护模式 |
| 天气 | Open-Meteo（已全球） | 同左 | 无缺口 |
| 签证 / 入境 | 内置常识表 + 提醒 | 同左；不接 Sherpa 等商用 API（贵且我们只做提醒不做权威承诺） | 维持既定边界 |

**路由策略**：目的地库每个城市标注 `geoSource: "amap" | "google"`（港澳台标 amap 优先、google 兜底），域检索按标注走，不做运行时自动探测——与 6.2 中"人工维护清单"的决策一致。EvidencePack 的证据源同理按城市标注（国内高德详情，海外 TripAdvisor）。

**成本注记**：Google Maps 与 TripAdvisor Content API 均有免费额度（Google 每月 $200 等值、TripAdvisor 5000 次/月），个人使用量级内为零成本；超量后这两个域是最先需要加缓存的（POI 详情缓存 7 天在 6.1 已有）。

## 8. 风险与开放问题

- **LLM 成本**：草案 1 次 + 批注增量的调用模式下，单次旅程规划估算 <¥1；行中轻量调用用低档模型。若用户量上来需要加缓存层（同目的地素材检索结果缓存 7 天）。
- **高德 vs Google 的目的地覆盖分界**：建议以"目的地库人工维护清单"为准，库内城市标注首选 POI 源，不做自动路由。
- **多设备**：M1 用 JSON 导出/导入过渡；何时上账号体系取决于是否有多人使用需求，本文不预设。
- **隐私**：画像含身体约束（晕车等）属敏感信息，保持本地存储时风险低；一旦上服务端需要重新过一遍隐私设计。
