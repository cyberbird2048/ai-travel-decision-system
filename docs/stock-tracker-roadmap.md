# 股票追踪系统 — 持续优化迭代路线图

MVP 已落地（`stock-tracker/`）。本文档规划后续迭代方向，按"先提高判断质量，再扩覆盖面，最后做体验"的顺序排列。所有 token 消耗大的任务延续分工：**Haiku 过滤/提取/汇总，Sonnet 分析/写作**。

---

## 迭代原则

1. **系统的产出是"判断"，不是"报告"。** 每次迭代先问：这个功能能让方向灯更早变黄、还是让报告更长？只做前者。
2. **每个新数据源先问信噪比。** 数据源越多，Haiku 过滤成本越高、误报越多。加数据源要配套加过滤规则。
3. **用自己的历史判断做回归测试。** 档案存 git 的最大价值：任何 prompt 改动都能在历史数据上重放对比。

---

## Phase 1：数据源补全（让判断有据可依）

| 功能 | 说明 | 模型分工 |
|---|---|---|
| SEC EDGAR 接入 | 10-K/10-Q/8-K 全文，替代 yfinance 的浅层快照。财报 PDF 直接喂给 Sonnet 分析（PDF 原生输入） | Haiku 定位关键章节（MD&A、风险因素 diff）→ Sonnet 精读 |
| 13F 机构扫描 | 每季拉取 config 中机构名单的持仓变动，只报增减仓 >20% 或新建/清仓 | Haiku 提取变动 → Sonnet 汇总写入 institutions.md |
| 财报电话会 transcript | 提取管理层承诺清单，下季核对兑现（喂给 milestones 核对流程） | Haiku 提取承诺 → Sonnet 核对言行一致性 |
| 风险因素 diff | 年报"风险因素"章节逐年 diff——公司自己新增的风险往往是最早的预警 | 纯文本 diff + Haiku 摘要变化 |
| Batch API | 所有定时任务改走 Message Batches（半价），实时性不重要 | 全部任务 |

## Phase 2：事件驱动（从定期刷新到即时响应）

- **触发器**：8-K 公告、股价单日 ±10%、财报发布日、watch item 相关新闻突增。
- **分级响应**：触发后先 Haiku 判断严重度（1-5 分），≥3 分才调 Sonnet 做事件分析（判断是否影响论点/方向灯，是否需要提前跑季度复查）。
- **实现**：GitHub Actions 每日扫描时顺带检查触发条件即可，不需要实时基础设施。

## Phase 3：判断质量（系统的核心竞争力）

1. **方向灯变更需要"两票"**：Sonnet 提议变灯后，用一次独立的 Sonnet 调用做对抗验证（"请反驳这个变灯理由"），反驳不成立才生效。防止单次分析的噪音把灯打黄。
2. **判断回测**：每季度把 6/12 个月前的 dashboard.json 和当时的分析报告翻出来，对照实际发生的事，由 Sonnet 打分：哪些预警对了、哪些漏了、哪些是误报。结果写入 `lessons.md`。
3. **经验库（lessons.md）**：回测得出的教训作为后续所有分析的附加上下文——"上次我在 X 上过度乐观，因为只看了多头证据"。这是系统随时间变强的机制。
4. **Prompt 回归测试**：改分析 prompt 前，用 git 里的历史档案 + 当时的新闻重放一遍，对比新旧 prompt 的输出质量再合入。
5. **数字防幻觉**：Sonnet 报告中的所有财务数字，用脚本回查 fundamentals.json / 原始财报核对，对不上的标注 ⚠️。

## Phase 4：覆盖面扩展

- **观察池分层生效**：holdings 每日扫描 + 季度深度；focus 每周扫描 + 半年深度；watch 只跑月度 Haiku 摘要。tier 直接控制 cron 频率和模型档位。
- **上下游联动**：观察池内公司互为上下游时（如 AAPL ↔ TSM），一次财报分析同时更新两份档案的 valuechain 信号，数据采集去重。
- **行业档案**：同行业 ≥3 只股票时建 `industries/<name>.md`，行业级变化（技术替代、监管）只分析一次，各公司档案引用。

## Phase 5：呈现与复盘体验

- **静态总览页**：读所有 dashboard.json 生成一页方向灯矩阵（GitHub Pages），一眼看全组合；灯变色的股票置顶。
- **推送**：方向灯变色 / Kill Criteria 触发时发 Telegram/邮件（周报常规内容不推送，只推变化）。
- **判断演变视图**：`git log -p stocks/AAPL/thesis.md` 的可读化——展示论点如何随时间修正，年度复盘时用。
- **年度复盘流程**：每年一次 Sonnet 全档案重审 + 估值锚三档更新 + 能力圈标签复核，输出年度信件式总结。

## Token 成本持续优化

| 手段 | 说明 |
|---|---|
| Batch API | 定时任务全量迁移，直接省 50% |
| Prompt caching 分层 | 档案按稳定性排序：business.md（几乎不变）在前，news_log 尾部在后，缓存前缀最大化 |
| 增量上下文 | 季度分析只喂"档案摘要 + 本季新数据"，不重复喂十年历史；档案超长时由 Haiku 先做摘要版 |
| news_log 滚动压缩 | 超过 90 天的日志由 Haiku 压缩成月度摘要，控制档案体积（也控制缓存写入成本） |
| 严重度分级 | 事件先 Haiku 打分，多数事件不进 Sonnet |
| 成本监控 | 每次调用记录 usage 到 `costs.jsonl`，周报附本周 token 花费，超预算自动降频 |

## 建议迭代顺序

```
第 1 步  Batch API + 成本监控          （先把成本地基打好，后面放心加功能）
第 2 步  EDGAR + 财报电话会承诺提取     （判断质量最依赖的数据源）
第 3 步  事件驱动 + 严重度分级
第 4 步  方向灯两票制 + lessons.md 回测 （系统开始"越用越聪明"）
第 5 步  13F、观察池分层、静态总览页
第 6 步  年度复盘流程
```

每步都独立可用、独立验证——跑两周看误报率和成本再进下一步，避免一次堆太多功能导致噪音失控。
